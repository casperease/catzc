# ADR: File meta — one block of derived facts, in the carrier each kind of file has

## Rules: ADR-REPO-FILEMETA

### Rule ADR-REPO-FILEMETA-HEADPOLICY

Every file on disk is **format-managed**: a `Format-*` command covers it and decides its **head policy**, whether it carries one **meta
block** and which, and a file no format command covers is a finding. A file is covered when its file language has a formatter or states its
`no_formatter` reason, or when `file-carriers.yml` declares a file class for it. The default is no head; a head is printed only where it
carries a fact worth its lines. A **generated file**, Markdown included, carries the head with the do-not-edit warning, and while git tracks
the file the head also carries `with_body_sha`, the body it is immutable with, and nothing else; an untracked generated file carries the
warning only, no sha ([ADR-REPO-FILEMETA-COMPOSEDFILES](#rule-adr-repo-filemeta-composedfiles)). An **authored file tracked in git**, a
source, config or template of any class, Markdown included (a Markdown doc is a config subtype of code, so one rule serves every authored
class), carries a head only when it has (1) a comment page under `docs/references`, shown as `docs`
([ADR-REPO-FILEMETA-FEWLINKS](#rule-adr-repo-filemeta-fewlinks)), or (2) rule codes to cite, the codes the file and its comment page cite,
shown as `cites` and counted as `drs_total` ([ADR-REPO-FILEMETA-FILEISNODE](#rule-adr-repo-filemeta-fileisnode)), and nothing else: no
`with_body_sha`, no `test` or `code` edge. Such a head opens with a `warning` line naming the command that writes it, "Header is generated
by Format-FileMeta via Format-Code; do not change it", declared once in `file-meta.yml`, and a file with no fact to show carries no head for
the warning alone. A binary file is format-managed with no head possible. Every other file carries no head, and a `Format-*` run removes a
head the policy does not call for. The policy has three values, set per file class in `file-meta.yml`: **facts**, the default, a block
holding the facts above, and none when every fact is empty; **forbidden**, no `catzc` block at all, for an agent definition, whose front
matter belongs to the tool that loads it, and for a diagram declaration; and **config**, a block holding only the authored `config` part,
for a capability definition and a slide, which keep their own tool's front matter as authored
([ADR-REPO-AGENTS-NAMEDMODEL](agent-definitions.md#rule-adr-repo-agents-namedmodel)). A file whose block disagrees with its policy, absent
where the policy calls for it or present where it does not, is a finding. The block holds the facts the tooling owns about the file, written
into the file's carrier. A Markdown file's carrier is the reserved front-matter key `catzc`, holding a generated file's head under
`immutable`, an authored file's edges under `edges` ([ADR-REPO-FILEMETA-FILEISNODE](#rule-adr-repo-filemeta-fileisnode)) and a capability's
authored config contributions under `config`
([markdown-config-contributions](../configuration/markdown-config-contributions.md#rule-adr-conf-mdcontrib-configcontribution)). The key
sits at the top level, or, where another tool validates the top level of the front matter and leaves one key of its own free for foreign
data, nests under that key at the key path the carrier registry declares (`key`, such as `metadata.catzc` for a capability); the block's own
key is `catzc` either way, and a parent key written as a flow mapping or a scalar is the author's to open up, never rewritten. A code file's
carrier is its meta head ([code-file-meta](code-file-meta.md#rule-adr-repo-codemeta-codefilehead)). The block is the only part of the file
the tooling owns: every other front-matter key belongs to the tool that reads it, and the tooling never reads, orders or rewrites one.

### Rule ADR-REPO-FILEMETA-METAKIND

A **meta kind** is one entry of the meta-kind registry (`file-meta.yml`), validated by its own C# type, with every default declared once on
that type ([ADR-AUTO-DEFAULT-ONERESOLUTIONORDER](../automation/sensible-defaults.md#rule-adr-auto-default-oneresolutionorder)). An entry
names the kind's id, its direction (`imprint` writes derived facts into the file, `gather` reads config contributions out of it), the files
it applies to, the keys it owns and their order, and, for a gather kind, the config it feeds. Globs live in one place: the registry's
ordered `classes`, where a file is the first class whose globs match it, or `other` (ADR-REPO-FILEMETA-ROLE). A kind selects files by class
and language (`select`, entries of `classes` with at most one `*` and `languages` from the file-language registry) and never by glob, and a
kind that selects nothing applies to every file, such as the path. A setting that names files does so by class too, and defaults to the
classes its kind selects. The carrier registry decides which files carry a block at all. Which kinds exist is data, never a list inside an
engine.

- [The meta-kind registry](#the-meta-kind-registry)

### Rule ADR-REPO-FILEMETA-IMPRINTEDPARTS

The `edges` part is imprinted by `Format-FileMeta` and is byte-identical on every run: keys in the registry's order, values in canonical
form, no timestamp and no run identifier. The `immutable` part is no imprinted part: only a generated head has it, and its writer writes it
([ADR-REPO-FILEMETA-COMPOSEDFILES](#rule-adr-repo-filemeta-composedfiles)). A hash is allowed only when it changes exactly when something a
reader cares about changes: `with_body_sha`, the hash of the body below the head, opens the head of a generated file git tracks. An authored
head carries none: a body hash there changes on every edit and tells a reader nothing, so the imprint writes only the edges
([ADR-REPO-FILEMETA-HEADPOLICY](#rule-adr-repo-filemeta-headpolicy)). A hash an author keeps in the `config` part is the author's, left
alone and never maintained. A second run changes no file. The output is stable under the formatter of the file's language, so the formatter
and the imprint never undo each other
([ADR-REPO-FORMAT-GENERATEDARTIFACTSFORMATTED](uniform-formatting.md#rule-adr-repo-format-generatedartifactsformatted)).

- [Imprinted, never hand-edited](#imprinted-never-hand-edited)

### Rule ADR-REPO-FILEMETA-SUBSCRIBEBYFUNCTION

A module subscribes to a meta kind by shipping a function named for it, found by convention as `Assert-<Name>Config` is
([ADR-CONF-LOADING-POWERSHELLVALIDATOR](../configuration/module-config-loading.md#rule-adr-conf-loading-powershellvalidator)):
`Get-<Kind>FileMetaFact` for an imprint kind and `Get-<Kind>MarkdownConfigContribution` for a gather kind, or a function the entry names.
`Test-FileMetaProcessors` fails a kind with no function and a function no kind names. A new kind is a registry entry and a function file,
never an edit to the engine ([ADR-AUTO-EXTEND-ADDNOTEDIT](../automation/open-closed-architecture.md#rule-adr-auto-extend-addnotedit)).

- [Subscribing a kind](#subscribing-a-kind)

### Rule ADR-REPO-FILEMETA-KINDSCOPE

The scope of a kind is the files it selects, less the files `.gitattributes` marks `linguist-vendored`, `linguist-generated`,
`catzc-fixture` or `catzc-contract`, and those it marks `-catzc-meta`. For Markdown the globs match the file class of the Markdown title
([ADR-REPO-FORMAT-MARKDOWNTITLE](uniform-formatting.md#rule-adr-repo-format-markdowntitle)). A new exception is declared in the
`.gitattributes` source, never in a list of the gate's own. The imprinted part, `edges`, is wholly the engine's: a key no kind owns there is
dropped on imprint, and a key a kind owns is rewritten from its fact. Only the authored `config` part keeps keys no kind owns, as the
author's, validated against its kind and kept as written, and a section of an authored block that is neither `edges` nor `config` is a
finding the author fixes.

- [Scope](#scope)

### Rule ADR-REPO-FILEMETA-PUREPARTS

The pure parts, the C# types, the carrier parsers and renderers and the file scanner, live in modules below `Catzc.Base.Config`, one per
carrier, that declare only `Catzc.Base.Repository`, `Catzc.Base.Objects` (every type renders through its console text) and
`Catzc.Base.Asserts`. Those modules read no config: every declaration reaches them as a parameter. The registry, the processors and the
commands that read the registry live in a module above `Catzc.Base.Config`, which reads the registry through `Get-Config` and passes it
down. `Get-Config` calls the scanner with the globs from the config registry, so the reader never depends on the module that reads the
meta-kind registry ([controlling-module-dependencies](../automation/controlling-module-dependencies.md)).

### Rule ADR-REPO-FILEMETA-COMPOSEDFILES

A file the automation composes whole — a root-config copy, a generator's output, a `.gitkeep` — carries the **generated-file head** instead
of an imprinted block. Its writer composes the content bare and writes the head through the one head function, in the carrier the file's
class has, tracked or not. The head holds, in this order, `with_body_sha` while git tracks the file (the hash of the content below it,
whatever the file's language and carrier, so the file says which text its writer composed and the drift check compares the stamp with the
hash of the content before it compares the content) and the `warning`
([ADR-REPO-FILEMETA-PROVENANCEINHEAD](#rule-adr-repo-filemeta-provenanceinhead)), and nothing else: no role, track, generator, source, edge
or `cites`. Every other fact about the file, the command that composed it and the authored files it comes from included, is derived on
demand from the writer registry. A generated file is told from an authored one by its writer's entry in the writer registry
(`generated-files.yml`) and its `linguist-generated` attribute, never by a kind of its own and never by its head
([ADR-REPO-FILEMETA-NOREADBACK](#rule-adr-repo-filemeta-noreadback)). No writer hand-words a banner. The imprint engine leaves these files
alone ([ADR-REPO-FILEMETA-KINDSCOPE](#rule-adr-repo-filemeta-kindscope)), since the writer owns every byte of them. A comment page is no
generated file: it is an authored file ([ADR-REPO-COMMENTS-PAGEISAUTHORED](comments-in-docs.md#rule-adr-repo-comments-pageisauthored)), so
the head policy gives it a head only when it cites rule codes ([ADR-REPO-FILEMETA-HEADPOLICY](#rule-adr-repo-filemeta-headpolicy)).

- [Generated files](#generated-files)

### Rule ADR-REPO-FILEMETA-PROVENANCEINHEAD

A generated file states its provenance once, in the head: the `warning`, the one string "Do Not Edit, this file is generated" that every
generated head carries, declared once as the default of the head's config type (`GeneratedHeadConfig`,
[ADR-AUTO-DEFAULT-ONERESOLUTIONORDER](../automation/sensible-defaults.md#rule-adr-auto-default-oneresolutionorder)) and written in the
file's own carrier. Which command composed the file and which authored files it comes from are the writer registry's to answer, never
written into the file. The body below the head is the content alone: no "generated from" line, no link to the source and no "edit the
source" note, since each would state in the file what the registry already answers.

- [Generated files](#generated-files)

### Rule ADR-REPO-FILEMETA-JSONCARRIER

A JSON file has no comments, so its carrier is an ignored top-level property that the carrier registry names (`//`, or `$comment` for a JSON
Schema): the first property of the object, holding the same `catzc` block as text. No file class keeps its block in a sidecar beside it: a
diagram declaration carries no head ([ADR-REPO-FILEMETA-HEADPOLICY](#rule-adr-repo-filemeta-headpolicy)), and a file class with no carrier
is an `exclude` entry of the carrier registry with the reason.

- [Property carriers](#property-carriers)

### Rule ADR-REPO-FILEMETA-FEWLINKS

The head is a map of facts about its own file, so it holds as few links to other files as possible, and only those that cost to derive and
truly define a relationship. A file has one **relative** edge, `docs`: its comment page under `docs/references`
([ADR-REPO-COMMENTS-ONELINEOFINSIGHT](comments-in-docs.md#rule-adr-repo-comments-onelineofinsight)), written as a GitHub-clickable link
whose target is the page's path from the file's own folder and whose text is the page's file name. A file has no `test` or `code` edge: a
test is found by convention, its stem under `tests/`, so a head would only repeat it. The page sits in the file's own docs section, never in
another module, so modules relate to each other by name and never through a file path (encapsulation), and a page knows its code by its
name, so it records no edge back. The edge and the rule that fills it are the `relative-edges` kind's settings in `file-meta.yml`, so a new
edge is a registry entry, never a new mechanism. The edge points at a page that exists on disk, and with no page it is left out. No file
carries a pointer of its own in its code: the head is the one place a file names its page.

- [Relatives](#relatives)

### Rule ADR-REPO-FILEMETA-ROLE

The **role** of a file is the part it plays, such as a test, a function, a config or a decision record, and never its language, track or
module, which are facts of their own, and it is derived on demand, never written into a head. A **subkind** narrows a role, such as a gate
among the functions, and a **file type** is the extension of the file's name, which tells the sorts of file inside one language apart. The
path of a file under its module (the whole path for a file in no module) is made of exactly three parts, its folder (none for a file
directly in the module), its name (the file's name without its file type, in kebab case) and its file type, each derived from the path on
demand and never written into a head, and deriving them asserts that they build the path back, so a path made of anything else stops the
run. The roles, their one-sentence definitions and the globs that select them are the entries of one registry, `file-kinds.yml`, local to
catzc and global to every file: the first entry whose globs match a path names its role, a path no entry selects is `other`, an earlier
entry that takes most of a later entry's files is an overlap the registry lists on purpose, a meta kind selects files by their role and
subkind and never by glob, and a consumer extends the registry with a config fragment. A provided contract pins the role and subkind names.

### Rule ADR-REPO-FILEMETA-FILEISNODE

A file is a node, and its meta block says two things about it, each in a part of its own. `immutable` holds the **place facts** a reader of
the head needs, and only a generated head has any: its `with_body_sha` while git tracks it and its `warning`, written by its writer
([ADR-REPO-FILEMETA-COMPOSEDFILES](#rule-adr-repo-filemeta-composedfiles)); an authored head has no `immutable` part, its parts are a
`warning` line naming its writer and its `edges` ([ADR-REPO-FILEMETA-HEADPOLICY](#rule-adr-repo-filemeta-headpolicy)). Every other place
fact, what the repository's own configuration makes of the file's location, is derived on demand from a registry and never shown. `edges`
holds what the file itself points at, each one an **edge**, a named relation leaving the file to a rule code or a file: `cites`, the rule
codes the file and its comment page cite outside their ` ```yml drawio ` blocks; `drs_total`, the count of distinct codes the file and its
page cite, those blocks included; and `docs`, its comment page; no `test` or `code` edge, since a test is found by convention. The fact
behind `cites` keeps every code, blocks included, and the `drs-codes` kind renders it into both keys, so a diagram's codes count toward the
total without filling the head's list. `edges` is imprinted and `immutable` is written by the file's writer, never by hand, and both are
fixed by the file: a place fact until the file moves or a registry changes, an edge until the file's text changes. An edge is written on its
source only, so the target holds no copy, and an edge is named for the relation, never for the type of its target. A tracked generated
file's `immutable` opens with `with_body_sha`, the hash of the body below the head
([ADR-REPO-FILEMETA-IMPRINTEDPARTS](#rule-adr-repo-filemeta-imprintedparts)). A head holds no `repo_status`: whether a file is generated is
told by the writer registry, and the states only git knows, edited, staged, committed and pushed, and `ready` (tracked and unchanged), are
computed on demand by `Get-RepoStatus` from git, read-only, since writing them would change them. An imprint kind of the registry writes the
`edges` part, a relation each.

- [Place facts and edges](#place-facts-and-edges)

### Rule ADR-REPO-FILEMETA-NOREADBACK

No command reads an imprinted fact back. A gate, a generator or a resolver that needs a place fact or an edge of a file derives it from the
registries, git, the disk and the file's body, so stripping every block changes no verdict, and every command works the same on a file with
a block and on one without. The imprint is the one reader of `edges` and a generated file's drift check the one reader of its `immutable`,
and each reads its part only to compare it with what would be written. A key another tool owns is read by that tool alone.

## Context

A file in this repository is more than its text. A Markdown agent definition declares a name, a description and its tools. An ADR sits in a
domain with a concern. A reference page belongs to a module. A C# type file and a PowerShell function file each belong to a module and a
place in its tree. Some of these facts are stated twice, once in the file and once in a registry that has to be kept in step, and some can
be computed from the file and the repository but are not written anywhere a reader could see them.

Two needs follow. Facts that can be computed are derived on demand, and a file shows only the few a reader needs to step on from it without
running anything: that a generated file is not to be edited, and where a file's rules and docs are. Values an author states belong where the
thing is, and a config can read them from there ([markdown-config-contributions](../configuration/markdown-config-contributions.md)). Both
need a place in the file that the tooling owns without touching what other tools own, and that place differs by kind of file, because front
matter is a Markdown convention and a code file has comments.

## Decision

A file carries one meta block, with the carrier its kind of file has. For Markdown the carrier is one reserved front-matter key, `catzc`,
with three parts: `immutable`, a generated file's head written by its writer, `edges`, written by the formatter, and `config`, written by
the author. For code the carrier is the meta head, with the same `immutable` and `edges` parts and no `config`. Which kinds of fact and
config exist is a registry. Who computes or reads each kind is a function a module ships.

### One block, two carriers

`One registry, a carrier per kind of file`

```yaml
---
name: example-check
description: Run one gate and report its verdict.
metadata:
  catzc:
    config:
      model_floor: haiku
---
```

A fact with no value, an empty list or an empty string, is the default of its key and is left out, so an absent key reads as the empty
value. `name` and `description` belong to the skill tooling and are untouched. A tool that reads front matter keeps working, because the
reserved key is one extra key it does not know. A tool that rejects a top-level key it does not know, as an editor's skill validator does,
still leaves one key free for foreign data, `metadata`, so for that file class the registry nests the block there (`key: metadata.catzc`):
the block keeps its own key and its parts, the tooling writes the parent key when the file lacks it and leaves every sibling under it alone,
and a parent written as a flow mapping cannot take a nested block, which is a finding for the author, never a rewrite. The parts never mix:
`immutable` is its writer's, `edges` is imprinted and rewritten, `config` is authored and kept. The code carrier, the form of a head in a C#
or PowerShell file, is in [code-file-meta](code-file-meta.md). Which carrier each file class has, or why it has none, is one registry,
`file-carriers.yml`, so a gap in the coverage is a visible entry.

### The meta-kind registry

`Kinds are data`

The registry says what exists; the engine knows no kind by name. An entry is small: an id, a direction, the classes and languages it
selects, keys and their order, and a target config for a gather kind. The globs are written once, in the ordered classes, so a set of files
is spelled in one place however many kinds read it. Adding a kind adds an entry, so the list of kinds is reviewed as data, in one file. One
registry serves every carrier, so there is one list of kinds to keep in step and one place a reader looks.

### Imprinted, never hand-edited

`The formatter owns edges`

An imprinted value is computed from the file and the repository, so a hand edit would only be overwritten, and a stale one would mislead.
The formatter writes the part in a fixed order and form, and the check fails when the file differs from what the formatter would write. No
timestamp is allowed, because a value that changes on every run makes every run a diff.

### Subscribing a kind

`The function is the subscription`

A module subscribes by adding a file. The convention names the function from the kind's id, as a config validator is named from its config.
The gate lists the orphans in both directions: a kind whose function is missing fails when the registry is read, and a function that matches
no kind is reported, so a rename cannot leave either side behind.

### Scope

`The same file classes as the title, and the code the registry names`

The meta block applies to the file classes whose content the repository authors, because the same classes are exempt for the same reasons:
vendored and generated files are not authored here, fixtures hold deliberately odd content, and contract assets are compared byte for byte.
One more attribute opts a single file out, for a file whose text is read verbatim by another tool.

### Layers

`Pure below the reader, wiring above it`

The reader of configs cannot depend on a module that reads configs. The carrier parsers, the renderers and the scanner take their inputs as
parameters and sit below the reader, where the reader can call them. The registry is a config and is read the usual way, by a module above
the reader that hands the declarations down.

### Generated files

`The writer owns the head, the engine stays out`

A generated file is rewritten whole on every run, and the drift check compares it with what its writer would compose now. If an imprint step
wrote the head afterwards, the two would disagree on every run, so the writer writes the head itself, with the same function every writer
calls. The head carries the one warning, so a reader is told not to edit the file in the same words everywhere, and the body stamp while git
tracks it; which command composed the file and which authored files it comes from are one question to the writer registry, so the head does
not repeat them. The carrier is the file class's own, named by the root-config entry or found from the file language, and no banner is
hand-worded, because a banner would be a second statement of what the head says.

### Property carriers

`JSON keeps the block in a property`

JSON has no comment syntax, and a leading `//` block makes it invalid, so the block is a property a reader of the data ignores. The property
holds the block as text, so one parser serves it as it serves a comment head, and a JSON Schema, whose `$comment` must be a string, takes
the same form. A diagram's facts are all in its declaration's body, its codes in `about.adrs`, so neither the picture nor the declaration
carries a block.

### Place facts and edges

`The node's place from the repository's configuration, the node's edges from its own text`

A file has two kinds of derived fact, and they answer different questions. Where does the repository put this file, and what does it make of
that place: its folder, its name, its role, its language, its track and its module, all read from registries the repository configures, so
the same file in another repository would have other values. And what does this file itself say it is related to: the rules it and its
comment page cite, and the page that holds its comments, read from the file and fixed by its text; its test is found by convention, so it is
no edge. The first is a property of the node, the second a set of directed, named edges leaving it. The place facts are asked of the
registries, so a head shows none of them, and on a tracked generated file the body hash alone stamps the text its writer composed. An edge
is named for the relation, so a new relation is a new name and a registry entry, and the target of an edge is spelled the same way wherever
it is read.

### Relatives

`A file names the one companion that costs to find, in the head`

A file has one companion a reader wants one step away that costs to find: the page that holds its moved comments. Its test costs nothing,
since the convention places it, its stem under `tests/`, so a head that named it would only repeat the convention and churn with it. Writing
the page as a link in the code would put a pointer in the file and a line to keep in step with the page. The head already holds derived
facts, so the page is an edge with a fixed name, the only relative edge, and the head stays a map of facts about its own file. The registry
holds the edge and its path rule, and an edge whose page does not exist is not written, so an entry in the head is always a working pointer.
The edge is written as a link, which an editor and GitHub follow in one click because its target is the page's path from the file's own
folder, the way both resolve a link.

### File kinds

`A file's role is one fact, and one registry names every role`

A file has a language, a track, a module and a role, and each is a fact of its own. Folding the language into the role, a Python script and
a PowerShell script as two roles, makes the same fact twice and a head that disagrees with itself. So the role says only what the file is
for: a test, a function, a config, a decision record. The registry holds each role with a one-sentence definition and the globs that select
it, in the order they are checked, with the subkinds of a role written under it, and it is the one place a glob for a file's role is
written. It is local to catzc and global to every file, so a generated head and every gate say the same thing about a file, and a consumer
extends it with a config fragment instead of editing it. A provided contract pins the names, so a consumer's tool may rely on them.

### A head shows the facts, never holds them

`The repository knows the facts; the head is their picture`

Every fact in a block is computed from something else: a registry, git, the disk or the file's own text. A command that reads the fact out
of the block instead trusts a copy that is right only when the file was last imprinted, so its verdict depends on when a formatter ran.
Deriving the fact every time gives one answer whether the file has a block, a stale block or none, and that is what lets the policy add or
remove blocks freely. The imprint reads the block only to say that it differs from what it would write.

### Head policy

`A head where a reader needs one, none where it only repeats`

A block is worth its bytes where a reader cannot easily derive what it says, and a head on every file is noise most readers and every agent
read past on each file they open, and churn on every edit of the body. So every file on disk is format-managed, the default is no head, and
a format run prints one only where it pays. A generated file carries the warning, so a reader is told not to edit it; while git tracks it,
its head also stamps the body its writer composed, the body it is immutable with, and an untracked generated file, which no commit compares,
carries the warning alone. An authored file tracked in git, Markdown as much as code and config, is opened on GitHub or in an editor by a
reader who wants its comment page and the rules it and its page cite one step away, so it carries `docs` and `cites` when it has them, and
nothing else: a body hash on an authored file changes on every edit and tells a reader nothing, and its test is found by convention. An
authored file with neither carries no head, so a format run clears the head it no longer calls for. A diagram declaration's facts are all in
its own body, so it carries none, and a binary has no place for one. An agent, skill or slide definition's front matter is its own tool's
keys, so the policy leaves it as authored; a capability keeps the authored `config` part its tool reads.

### How this is enforced

- **`Format-FileMeta`** imprints the `edges` part and `Test-FileMeta` fails any difference, in scope and in form.
- **`Test-FileMetaProcessors`** fails a kind without its function and a function without a kind.
- **`Test-FileKindReachability.Tests.ps1`** (`Catzc.Base.Globs`) fails a kind no tracked file reaches, and a kind mostly shadowed by an
  earlier one that the registry's `overlaps` does not pair it with (ADR-REPO-FILEMETA-ROLE).
- **`Test-ModuleDependency`** keeps the layers apart ([ADR-AUTO-DEPM](../automation/controlling-module-dependencies.md)).

## Consequences

- A computable fact is asked of the repository, and a head shows only the few a reader needs to step on, the same on every run: an authored
  head changes only when its citations or its page change, never on an edit of the body alone.
- A fact an author states is written once, in the file of the thing, and the config that needs it gathers it from there.
- Another tool's front matter is never touched, so an agent or skill file keeps working unchanged.
- A new kind of fact or config is a registry entry and a function, reviewed as data and as one file of code.
- The formatter and the pure scanners are testable on strings alone, because they read no config and touch no file.
