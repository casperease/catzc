# ADR: Cross-platform PowerShell — the language layer over cross-platform

## Rules: ADR-PWSH-XPLAT

### Rule ADR-PWSH-XPLAT-PWSHMEETSCROSSPLATFORM

PowerShell code meets [cross-platform](../cross-platform.md) (`ADR-AUTO-XPLAT`) through the rules below, enforced mechanically:
PSScriptAnalyzer's compatibility rules validate cmdlets and .NET types against the target-platform profiles at analysis time, before the
code ever runs on the other OS.

- [Analyzer coverage](#analyzer-coverage)

### Rule ADR-PWSH-XPLAT-PATHJOINPRIMITIVE

The path-joining primitive of [ADR-AUTO-XPLAT-NOPLATFORMPATHS](../cross-platform.md#rule-adr-auto-xplat-noplatformpaths) is `Join-Path`: use
it for all path construction, and never concatenate strings with `/` or `\`. It uses the correct separator for the current platform.

- [What breaks in practice](#what-breaks-in-practice)

### Rule ADR-PWSH-XPLAT-NOPLATFORMCMDLETS

Never use platform-specific cmdlets (`Get-Service`, `Get-WmiObject`, …) without a cross-platform alternative. If platform-specific behavior
is unavoidable, branch on the built-in `$IsWindows` / `$IsLinux` automatic variables and always implement both branches.

- [What breaks in practice](#what-breaks-in-practice)

### Rule ADR-PWSH-XPLAT-NOPLATFORMSHELL

PowerShell code meets [ADR-AUTO-XPLAT-NOPLATFORMSHELL](../cross-platform.md#rule-adr-auto-xplat-noplatformshell) with its native operations,
or with the `Invoke-Executable` wrapper around a tool that exists on both platforms — never `cmd /c` or `/bin/sh -c`.

- [What breaks the other way](#what-breaks-the-other-way)

### Rule ADR-PWSH-XPLAT-PATHFROMANCHORS

PowerShell code resolves a path from the anchors of
[ADR-AUTO-XPLAT-NOPLATFORMPATHS](../cross-platform.md#rule-adr-auto-xplat-noplatformpaths): the working root through `Get-RepositoryRoot`,
the code root through `Get-CatzcModuleRoot`, or the temp directory through `[IO.Path]::GetTempPath()`, then joined by
ADR-PWSH-XPLAT-PATHJOINPRIMITIVE. It never writes a literal `C:\` or `/tmp/`, and never reads a variable that one platform alone sets
(`$env:APPDATA`, `$env:USERPROFILE`).

- [What breaks in practice](#what-breaks-in-practice)

### Rule ADR-PWSH-XPLAT-INVARIANTCULTURE

PowerShell code formats and parses a machine-bound string
([ADR-AUTO-XPLAT-INVARIANTCULTURE](../cross-platform.md#rule-adr-auto-xplat-invariantculture)) with
`[System.Globalization.CultureInfo]::InvariantCulture` passed to `ToString` or `ParseExact`.

- [Culture in PowerShell](#culture-in-powershell)

### Rule ADR-PWSH-XPLAT-PATHCOMPARISON

PowerShell code compares paths ([ADR-AUTO-XPLAT-CASESENSITIVEFILES](../cross-platform.md#rule-adr-auto-xplat-casesensitivefiles)) as full
paths, each passed through `[System.IO.Path]::GetFullPath()`, and compares them ordinally and case-insensitively with
`[StringComparer]::OrdinalIgnoreCase` (or `[string]::Equals` with `[StringComparison]::OrdinalIgnoreCase`), never culture-sensitively. The
hazards are a case-sensitive operator (`-ceq`, `-clike`), a `.Equals` or `.StartsWith` call without a `StringComparison` argument, and two
paths compared before they are normalised.

- [Comparing paths](#comparing-paths)

### Rule ADR-PWSH-XPLAT-ONECODEPATH

The one code path of [ADR-AUTO-PARITY-SAMECLIBOTHENVIRONMENTS](../devbox-pipeline-parity.md#rule-adr-auto-parity-sameclibothenvironments)
is, in PowerShell, the dot-sourced `importer.ps1` for the session and the per-tool `Install-*` functions over `tools.yml` for the tools
([ADR-AUTO-DEPS-CISAMEINSTALLERS](../controlling-systemwide-deps.md#rule-adr-auto-deps-cisameinstallers)), run unchanged on a workstation
and in CI. `Install-DevBoxTools` orchestrates those functions on a devbox; a pipeline calls the same functions directly.

- [How this is enforced](#how-this-is-enforced)

### Rule ADR-PWSH-XPLAT-HANDBUILTCROSSINGS

The hand-built crossings [ADR-AUTO-PATH-CENTRALNORMALIZATION](../path-representation.md#rule-adr-auto-path-centralnormalization) forbids
are, in PowerShell, a `Join-Path $env:RepositoryRoot …` (or `Join-Path (Get-RepositoryRoot) …`) whose result is stored, returned, or logged,
and a `-replace '\\','/'` separator fix. A path leaves through `ConvertTo-RepoRelativePath` and binds through `Resolve-RepoPath`;
`Join-Path` onto an anchor is correct only on the line that binds the result.

- [What breaks in practice](#what-breaks-in-practice)

## Context

[cross-platform](../cross-platform.md) fixes the doctrine: everything runs on Windows and Linux, and a developer tests locally everything
that runs in CI. PowerShell 7+ is cross-platform by design, but the _code_ people write in it often is not: Windows-only cmdlets, .NET types
that do not exist on Linux, backslash separators, registry access, COM objects, shell-outs to `cmd.exe`. These work fine on the author's
machine and fail silently or loudly in CI. This ADR is the language layer — the concrete PowerShell hazards and the analyzer that catches
them before push.

### What breaks in practice

| Windows-ism                                            | Fails on Unix because                 |
| ------------------------------------------------------ | ------------------------------------- |
| `C:\path\to\file` hardcoded                            | No `C:` drive, no backslash paths     |
| `[Microsoft.Win32.Registry]`                           | Type does not exist on .NET Core Unix |
| `Get-Service`, `Get-WmiObject`                         | Cmdlets not available on Unix         |
| `cmd /c` or `Start-Process notepad`                    | Binaries do not exist                 |
| `$env:APPDATA`, `$env:USERPROFILE`                     | Variables not set on Unix             |
| `[System.IO.Path]::DirectorySeparatorChar` assumed `\` | It is `/` on Unix                     |
| Case-insensitive file lookups                          | Unix filesystems are case-sensitive   |

### What breaks the other way

| Unix-ism                                              | Fails on Windows because                     |
| ----------------------------------------------------- | -------------------------------------------- |
| `#!/usr/bin/env pwsh` shebang relied on for execution | Windows uses file associations, not shebangs |
| `chmod +x` permissions                                | NTFS does not have executable bits           |
| `/tmp`, `/dev/null` in paths                          | Not valid Windows paths                      |
| `apt-get`, `brew` assumed available                   | Windows uses `winget`                        |

### Culture in PowerShell

`ToString()` on a date or a number, and `[datetime]::Parse`, use the current culture, so a da-DK devbox and an invariant CI agent render and
read the same value differently. Passing `[System.Globalization.CultureInfo]::InvariantCulture` makes the format explicit at the call site.
Why the culture axis matters at all is the doctrine: [cross-platform](../cross-platform.md#rule-adr-auto-xplat-invariantculture).

### Comparing paths

Two strings that name the same file can differ in three ways: in case (`C:\Repo` and `c:\repo`), in form (`out\..\docs` and `docs`, a
relative and an absolute path), and in characters a culture-aware comparison treats as equal or ignorable. `GetFullPath()` removes the
second difference, and an ordinal comparison decides the other two by the characters alone, the same on every machine and in every culture.
PowerShell's own operators do not give that comparison. `-eq` and `-ieq` are case-insensitive on strings, but they compare in the invariant
culture, not ordinally: `'ab' -ieq "a$([char]0xAD)b"` is `$true`, because a culture-aware comparison ignores the soft hyphen. `-ceq` and
`-clike` are case-sensitive, so two spellings of one Windows path compare unequal. A `.Equals` or `.StartsWith` call without a
`StringComparison` falls back to a default the call site does not show: case-sensitive ordinal for `.Equals`, the current culture for
`.StartsWith`. Naming `[StringComparer]::OrdinalIgnoreCase` states the rule where it applies.

### Analyzer coverage

`How the analyzer catches platform breaks`

**PSScriptAnalyzer** validates cmdlets and .NET types against Windows and Ubuntu profiles at analysis time, catching Windows-only APIs
_before the code runs_ — in the L2 tests, on every developer's machine. The rules that do this (`PSUseCompatibleCmdlets`,
`PSUseCompatibleTypes`), their target profiles, and their on/off state are defined in `PSScriptAnalyzerSettings.psd1`, documented inline
(they are costly to run and may be toggled — the psd1 is authoritative).

**Why no macOS profile?** PSScriptAnalyzer's built-in compatibility catalog only ships with Windows and Ubuntu profiles — there is no macOS
catalog. In practice this is fine: macOS and Linux both run .NET on Unix, so the cmdlet and type surface is nearly identical. The Ubuntu
profile effectively covers macOS. If Microsoft ever ships a macOS catalog, we add it to the list.

**`Join-Path` and `[IO.Path]::Combine`** handle separators correctly on both platforms. Hardcoded `/` or `\` in paths is always wrong.

## Decision

PowerShell code constructs every path with `Join-Path` from a known anchor, uses no platform-only cmdlet or binary without a branch for the
other platform, expresses unavoidable platform logic as `$IsWindows` / `$IsLinux` branches, passes the invariant culture to every
machine-bound format and parse, and compares full paths ordinally and case-insensitively — all validated by the analyzer's compatibility
profiles before push.

### How this is enforced

- **PSScriptAnalyzer compatibility rules** — `PSUseCompatibleCmdlets` and `PSUseCompatibleTypes` flag cmdlets and .NET types not available
  on all target platforms. The rules, their profiles, and their on/off state live in `PSScriptAnalyzerSettings.psd1`.
- **L2 tests run locally** — developers run the same `Test-ScriptAnalyzer.Tests.ps1` test file that CI runs, so platform violations are
  caught before push, not in the pipeline queue.
- **One entry, everywhere** — `importer.ps1` and the per-tool `Install-*` functions are the same files on a workstation and in CI; a
  pipeline step calls them, never a CI-only script (ADR-PWSH-XPLAT-ONECODEPATH).

## Consequences

- Code that passes L2 tests locally on Windows is validated against Linux compatibility without needing a Linux machine.
- Platform-specific concerns are isolated to `Install-*` functions and branched on `$IsWindows` / `$IsLinux`; the rest of the codebase is
  platform-agnostic.
- Path handling is consistent everywhere — `Join-Path` from an anchor is the only way to build paths.
- New platforms (macOS) can be added by extending the `Install-*` functions without touching business logic.
