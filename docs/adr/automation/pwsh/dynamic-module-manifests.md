# ADR: Dynamic module manifests — the pwsh rules over open-closed-architecture

## Rules: ADR-PWSH-MANIFEST

### Rule ADR-PWSH-MANIFEST-OPENCLOSEDMODULES

The PowerShell module system realizes [open-closed-architecture](../open-closed-architecture.md) (`ADR-AUTO-EXTEND`)
mechanically: module manifests are a generated projection of the filesystem, and the one seam convention cannot guard — a duplicate function
name — fails the import before anything loads.

- [Why PowerShell](#why-powershell)

### Rule ADR-PWSH-MANIFEST-GENERATEDMANIFESTS

Never hand-maintain manifests: `.psd1` files are generated by `New-DynamicManifest`. The filesystem is the single source of truth for what a
module contains and exports.

- [Why PowerShell](#why-powershell)

### Rule ADR-PWSH-MANIFEST-MANIFESTSGITIGNORED

Generated manifests are gitignored, never committed. `New-DynamicManifest` recomputes each module's `<Module>.psd1` from the filesystem on
**every** import, writing only when the content differs (and deleting it when a module has no `.ps1` files left), so the manifest is a pure
derived artifact — `pwsh/**/*.psd1` is gitignored. The only committed `.psd1` files are the vendored third-party manifests under
`pwsh/.vendor/` and the authored analyzer settings `pwsh/.internal/assets/PSScriptAnalyzerSettings.psd1` (both negated in `.gitignore`),
which the platform does not generate.

- [Regenerated manifests](#regenerated-manifests)

### Rule ADR-PWSH-MANIFEST-ONEDEFINITIONPERNAME

Every function name resolves to exactly one definition. Two catzc modules cannot export the same name, and no catzc function may shadow an
already-imported vendored or built-in command — `Import-AllModules` fails fast on either before any module loads, since PowerShell would
otherwise let the module imported last silently win. Beyond exports, every function name — public or private — must be defined in exactly
one file across the repository, verified by an integrity test.

- [One function namespace](#one-function-namespace)

### Rule ADR-PWSH-MANIFEST-BUNDLECARRIESMANIFESTS

A bundle ([platform-bundle](../platform-bundle.md#rule-adr-auto-bundle-bundleisbuild)) carries the **runtime payload in merged
form**. Every selected module is its own folder holding a generated `<Module>.psd1` (`NestedModules` = the one merged file,
`FunctionsToExport` = the module's public functions only), a generated `<Module>.functions.ps1` that merges the module's `private/` and root
function files — named apart from the module, so the nested script module never shares the manifest module's name — and the module's side
folders (`configs/`, `assets/`, and the `types/` sources) copied verbatim — never its `tests/`. Beside the modules sit the `.internal`
loader, the vendored dependencies per policy under `.vendor/`, the **full** combined-types DLL under `.compiled/` with the unselected
modules' type sources under `.compiled/types/<Module>/`, the top-level `Catzc.psd1`, `Catzc.psm1`, and `Import-Catzc.ps1`, and `build.json`.
The payload is deliberately **broader** than the protection `live` aspect ([module-aspects](../../design/module-aspects.md)) — that aspect
excludes `assets/` to keep its identity isolated, but a running module needs its `assets/`. Shipping is default-deny: the `tests/` surface
never travels.

- [The merged module form](#the-merged-module-form)

### Rule ADR-PWSH-MANIFEST-ONEBUILDMODULE

A build is one PowerShell module, `Catzc`: a generated top-level `Catzc.psd1` exporting the selected modules' public functions, whose
`RootModule` is a generated one-line `Catzc.psm1` that dot-sources `Import-Catzc.ps1`
([pwsh-engine](pwsh-engine.md#rule-adr-pwsh-engine-buildentry)). That makes the placements of
[platform-bundle](../platform-bundle.md#rule-adr-auto-bundle-twoartifactinstall) ordinary PowerShell installs:
`Install-Catzc -Scope CurrentUser` copies the build into the user's module path, so `Import-Module Catzc` works from any shell, and
`Export-Catzc -To nuget` packs it into `out/pwsh/packages/` for a local-path `Install-PSResource`, with the vendored dependencies riding
inside its `.vendor/`, never as `RequiredModules`.

- [The package module](#the-package-module)

### Rule ADR-PWSH-MANIFEST-CLOSEDINFRASTRUCTURE

The infrastructure that stays closed (ADR-AUTO-EXTEND-ADDNOTEDIT) is, in PowerShell, the generated `importer.ps1` shim, the
`pwsh/.internal/` modules — `Catzc.Internal.Importer` (the load sequence), `Catzc.Internal.Bootstrap` (`Import-AllModules`,
`New-DynamicManifest`) and `Catzc.Internal.Vendor` (`Import-VendorModules`) — and the shared loader `Import-ModuleFiles.ps1`. A new function
file, module folder, or vendored module is discovered by them; none of them is edited to admit it.

- [Conventions in PowerShell](#conventions-in-powershell)

### Rule ADR-PWSH-MANIFEST-NOMODULEIMPORTS

No catzc module imports another. Dot-sourcing `importer.ps1` (ADR-PWSH-ENGINE-IMPORTERDOTSOURCED) imports every module into one global
function namespace, so a function calls any catzc function by name — no `Import-Module`, no `using module`, no `RequiredModules`, no
hand-written export list. This is zero ceremony (ADR-AUTO-ZERO-ZEROCEREMONYAUTOMATION) in PowerShell; which module may call which is the
declared graph (ADR-AUTO-DEPM-CODEBUILTFROM), never an import statement.

- [Conventions in PowerShell](#conventions-in-powershell)
- [One function namespace](#one-function-namespace)

### Rule ADR-PWSH-MANIFEST-VISIBILITYISLOCATION

Visibility is location (ADR-AUTO-EXTEND-MANDATORYCONVENTIONS, ADR-AUTO-ZERO-MISTAKESHARDTOMAKE). `New-DynamicManifest` exports every root
`*.ps1` of a module, apart from `*.Tests.ps1`, under its file's base name, and loads every `private/*.ps1` without exporting it. No
attribute, `Export-ModuleMember` call, or hand-written list decides what is public.

- [Regenerated manifests](#regenerated-manifests)

### Rule ADR-PWSH-MANIFEST-CROSSMODULECALLS

Because every module shares one function namespace (ADR-PWSH-MANIFEST-NOMODULEIMPORTS), a cross-module call resolves at runtime whether its
edge is declared or not, so the function-call edges of the module graph (ADR-AUTO-DEPM-UNIFIEDGRAPH) are read from the source:
`Get-FunctionDependency` parses every non-test `.ps1` under `pwsh/` and maps each command call to the module that defines it, and
`Get-ModuleDependency` collapses the cross-module calls into the module edges `Test-ModuleDependency` checks.

- [Conventions in PowerShell](#conventions-in-powershell)

## Context

[open-closed-architecture](../open-closed-architecture.md) fixes the doctrine: grow the system by adding files and folders, never
by editing the infrastructure that discovers them. This ADR realises it in pwsh — the manifest and namespace mechanics that make the
doctrine hold in this module system, in the source tree and in the installed build.

PowerShell module systems typically require hand-maintained manifests, explicit import lists, or registration steps. Each new function means
editing a `.psd1`, updating an export list, or adding a line to a loader script. These edit-to-extend workflows create merge conflicts,
stale manifests, and "I added the function but forgot to export it" bugs. The bootstrap module eliminates that entire class of problems by
generating manifests dynamically from the filesystem.

### Why PowerShell

`Why this matters for PowerShell specifically`

**No linker catches missing exports.** In compiled languages, a missing export causes a build error. In PowerShell, a function that exists
in a file but is missing from `FunctionsToExport` silently does not load. The caller gets a confusing "command not found" at runtime — often
in CI, often after the PR already merged. Dynamic manifest generation eliminates this failure mode entirely.

**Hand-maintained lists rot.** A `.psd1` manifest with an explicit `FunctionsToExport` list is a second source of truth that must stay in
sync with the actual files. Every rename, move, or delete requires updating both the file and the manifest. People forget. Reviews miss it.
The list drifts. Filesystem-driven discovery means the filesystem _is_ the manifest — there is no second source of truth to keep in sync.

**Merge conflicts on shared files.** When every new function requires editing a central manifest or loader, two developers adding functions
in parallel will conflict on that file. The conflict is trivial but annoying, and it blocks CI. Convention-based discovery means parallel
additions never touch the same file.

**Onboarding cost compounds.** "To add a function, create a file, then edit the manifest, then update the export list, then add it to the
loader" is four steps where one would do. Each extra step is a place a newcomer can get stuck. "Drop a `.ps1` file in the folder" is
self-evident.

### Conventions in PowerShell

The doctrine's conventions each have one PowerShell form. The closed infrastructure is the importer shim and the `.internal` modules, which
know conventions and no content. A module is a folder whose manifest is derived, and a function is a file whose base name is its export. And
because every module lands in one global namespace, a caller never imports what it calls: the import statement a PowerShell author would
write by habit has no place here, so the module graph cannot be read from imports and is read from the calls themselves.

### Regenerated manifests

`Manifests are a regenerated, gitignored artifact`

A module's `.psd1` is not source — it is a projection of the module's `.ps1` files, recomputed every time the importer runs.
`Import-AllModules` calls `New-DynamicManifest` for each module directory immediately before `Import-Module`, deriving
`<Module>/<Module>.psd1` directly from the current filesystem: every root `*.ps1` (excluding `*.Tests.ps1`) becomes an exported function,
every `private/*.ps1` a non-exported one. The files are listed, `private/` first and then the root, each group ordinal, in the manifest's
`PrivateData.CatzcFiles`; its one `NestedModules` entry is the shared loader `pwsh/.internal/assets/Import-ModuleFiles.ps1`, which parses
each listed file in memory and dot-sources it into the module's session state. Loading each file as its own nested script cost about 3 ms
per file on top of its parse — most of the import — while the parsed script block keeps the source file and line for `Get-Command`, errors
and stack traces. The file is written only when the recomputed content differs — a clean tree costs a read per module and no write, which is
also what lets Test-Automation's parallel workers import concurrently without racing the manifest files. A directory that has lost all its
`.ps1` files has its stale manifest deleted in the same loop. The manifest is never read as an input and never hand-edited; the filesystem
of `.ps1` files is the single source of truth, and the manifest is its output.

Because the manifest is regenerated from scratch on every import, committing it would be committing a build output. It would drift from the
`.ps1` files on any branch that adds, renames, or moves a function, and produce noisy, conflict-prone diffs that say nothing the directory
listing does not. So the generated manifests are gitignored, with negations for the vendored case and the authored analyzer settings:

```gitignore
pwsh/**/*.psd1
!pwsh/.vendor/**/*.psd1
!pwsh/.internal/assets/PSScriptAnalyzerSettings.psd1
```

The exception is real source from the dependency's perspective: a vendored third-party module under `pwsh/.vendor/` ships its own
author-written `.psd1`, which the platform does **not** generate and which must be committed for offline reproducibility (see
[vendor-toolset-dependencies](vendor-toolset-dependencies.md)). Ours are derived; theirs are vendored source — which is exactly why one is
gitignored and the other is committed.

### One function namespace

`One global, collision-free function namespace`

Convention-as-source-of-truth carries one assumption: that a function name means exactly one thing. The export list is derived from file
names (`Get-Foo.ps1` exports `Get-Foo`) and every module imports into the global scope, so the whole repository shares a single function
namespace. Two modules that both export `Get-Foo` do not error — PowerShell lets the module imported last silently shadow the other, and a
caller gets whichever module sorted last. The same holds against the modules imported before ours: a function named like a vendored or
built-in command shadows it just as silently.

This is the one open/closed seam where "non-conforming code is invisible" does not hold — both definitions are discovered, and one quietly
wins. So the import enforces it directly. Before any module (or C# type) loads, `Import-AllModules` computes the names each module would
export and fails fast, naming every collision, when:

- two catzc modules would export the same name, or
- a catzc function would shadow an already-imported shipped command — one from a vendored module or a built-in. The shadow check is scoped
  to shipped commands by module path, so a user's unrelated session module never blocks the import.

The import-time guard limits its scope to the set the manifests export — module-root functions always, `private/` functions under
`-ExportPrivates` — because that is the set a load can actually break. The repository is stricter than that: an integrity test
(`Test-Automation.Tests.ps1`) parses every module file and fails if any function name, public or private, is defined in more than one file.
Reusing a private name across modules would not break an import (privates are module-scoped), but the repo forbids it anyway so the
one-function-per-file promise — `Get-Foo.ps1` is the file, anywhere in the tree — holds for private helpers too. `Test-FunctionDependency`
independently fails on a duplicate public name as well.

### The merged module form

In the installed build every selected module is **its own PowerShell module of the same name** — same public functions, same private
functions, same configs and assets, its own `$script:` scope ([run-modes](../../design/run-modes.md)). Only its on-disk form differs: one
manifest and one merged function file instead of a folder of function files. For each selected module, `Build-Modules` merges the function
files into one `<Module>.functions.ps1` — `private/*.ps1` in ordinal order, then the root `*.ps1` in ordinal order, the same order the
source manifest's `PrivateData.CatzcFiles` lists, so load semantics are identical — each file verbatim behind a
`# source: pwsh/<Module>/<path>` marker line, so an error line in the merged file maps back to its source file. The module's manifest is
generated by the same canonical emitter that the source mode uses, listing that one file and exporting only the public functions; privates
stay internal. The merged file keeps the `.ps1` extension, so the module's functions share one session state as they do in source
([use-ps1-not-psm1](use-ps1-not-psm1.md)), and it is named apart from the module, so the nested script module and the manifest module never
share a name.

The side folders travel verbatim, including `assets/` (install scripts, hook starters, packaged data) and the `types/` sources the load-time
types guard re-verifies. The vendored modules are copied verbatim from `.vendor/` per `vendor_policy` — `runtime` ships `powershell-yaml`
only; `full` also ships Pester and PSScriptAnalyzer, which the build run needs — and are never re-downloaded or republished. Default-deny
keeps the verification surface out: no `tests/` tree travels.

### The package module

The build's modules are not nested modules of one package manifest: the importer loads them one by one, in the order the types need
([pwsh-engine](pwsh-engine.md#rule-adr-pwsh-engine-buildentry)), each with its own manifest and scope. The package manifest `Catzc.psd1`
exists so the build is also an ordinary PowerShell module that the module path and PSResourceGet understand. Its `RootModule` is one line
that dot-sources `Import-Catzc.ps1`, so `Import-Module Catzc` runs the one entry and there is no second loader. A NuGet package of the build
declares no `RequiredModules`: its dependencies are the vendored copies inside it, so installing it fetches nothing.

## Decision

Module manifests are generated by `New-DynamicManifest` from the filesystem on every import and never committed; the import fails fast on
any duplicate export or shadow of a shipped command; and an integrity test holds every function name — public or private — to exactly one
defining file. In the installed build each module is one generated manifest and one merged `.ps1`, and the build as a whole is the `Catzc`
module, whose root module dot-sources the build's entry.

### How this is enforced

- **`New-DynamicManifest`** — the single manifest generator, driven by `Import-AllModules`; there is no hand-edited manifest to drift.
- **`Import-AllModules`** — the pre-load collision and shadow check, failing the import with every collision named.
- **`Test-Automation.Tests.ps1`** + **`Test-FunctionDependency`** — the repository-wide unique-name integrity checks.
- **`Get-FunctionDependency`** + **`Get-ModuleDependency`** — read the cross-module call edges from the source for `Test-ModuleDependency`.
- **`.gitignore`** — `pwsh/**/*.psd1` with the `.vendor` negation keeps derived manifests out of git and vendored ones in.
- **`Invoke-ModuleBuild`** (`Catzc.Internal.Builder`) — writes each module's manifest and merged `.functions.ps1`, the package `Catzc.psd1`
  and `Catzc.psm1`, and `Assert-CatzcBundle` checks that every module has its manifest and merged file and that every manifest export
  resolves to a function in that file.

## Consequences

- Adding a function never touches a manifest, an export list, or a loader — the file is the registration.
- The whole repository shares one function namespace, and it is collision-free by construction: a duplicate export — or a function that
  would shadow a vendored or built-in command — fails the import with a named error instead of silently shadowing.
- `git status` never shows generated manifests, and a branch switch never conflicts on them.
- The cost is that the manifest is invisible as an artifact: a reader who wants a module's export list reads the directory (which is the
  point), or lets an import materialize the `.psd1`.
- A cold import of an installed build opens one function file per module, and error line numbers inside it point into the merged file; the
  `# source:` markers map them back.
