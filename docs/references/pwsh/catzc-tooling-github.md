# Catzc.Tooling.Github

The repository's GitHub integration: everything that faces GitHub, as a platform that reads our files and as a remote that stores our
history. Two jobs make it up. It holds the GitHub-facing contracts — what GitHub requires of the files it reads, kept under
`contracts/catzc/<version>/Catzc.Tooling.Github/`
([ADR-REPO-CONTRACT-LAYOUT](../../drs/repository/api-contracts.md#rule-adr-repo-contract-layout)). And it erases a token — a leaked secret,
or a name being scrubbed — from a GitHub repository's entire history and its remote object store, then proves it is gone. Erasure needs a
module of its own because an ordinary force-push erases nothing: the old commits become unreachable but stay stored on the server until
GitHub garbage-collects them, so a fetch of a known old SHA keeps resolving. Deleting and recreating the repository is the only way to
destroy those remote objects. It owns that whole workflow — rewrite the local history token-free, assert the irreversible step is safe,
purge and republish on GitHub, and verify the result across every surface a token can hide in (file content, file paths, and commit
messages). It is not a general git or `gh` wrapper, and it drives every external command through the process boundary in
[Catzc.Base.Execution](catzc-base-execution.md).

### responsibility:1 — Remote purge and publish

Making a clean local history the remote's sole history and destroying the old object store with it. Two entry points cover the two starting
points: hard-purging a repository that already exists — delete it, recreate it (optionally under a new name), push, and re-scan — and
publishing a clean tree to a brand-new repository that must not already exist. Both are safe by default: they run the preflight and return a
plan, mutating nothing until armed with an explicit confirm-repo value equal to the target. After pushing, each reads the refs the new
remote advertises (`git ls-remote`) and requires every one to point at the scanned local commit. A commit's hash names its whole history, so
a match proves what the server stored without downloading it, and a ref at any other commit fails as history the scan never covered. Pushing
a whole history outlasts an ordinary call, so both declare their own time limit and bound the push and the remote read with it.

### responsibility:2 — Local history rewrite

Producing a local history that no longer contains the token, by one of two routes. The preferred route rebuilds the history from the current
(already-clean) working tree as a fresh, backdated, single-author orphan history: because every synthetic commit is authored from a tree
that no longer holds the token, it appears in no blob, path, or message, so there is nothing left to scrub and no residual objects. The
fallback route scrubs the token in place with git-filter-repo, rewriting blob content and commit messages — second-choice because it leaves
the old commits as unreachable objects until GitHub garbage-collects and cannot reach a token that lives in a file _path_. Both routes are
destructive to local history and expect a `git bundle create --all` backup to exist first.

### responsibility:3 — Purge preflight

Asserting, up front and fail-fast, every precondition the irreversible remote step depends on, so the destructive path never runs against a
repository it cannot safely purge. The checks: `gh` is installed and authenticated; the token carries the `delete_repo` scope; the caller
owns the repository and it is not itself a fork; it has no forks of its own (a fork keeps the old objects alive elsewhere); the local origin
points at the repository about to be deleted; and a backup bundle exists and passes `git bundle verify`. It mutates nothing — it throws a
specific, actionable error for whichever check fails first.

### responsibility:4 — Token-absence verification

The read-only primitive behind every purge: proving a token is absent across all three surfaces it can survive in — file content (blobs),
file paths, and commit messages — over a ref's whole reachable history, not just the working tree. It returns a structured result naming any
residual hits so a caller can act on path-name residue a content scrub could not reach. The scan is one pass by the history scan in
[Catzc.Base.Git](catzc-base-git.md): every object is read once from a single git stream, and each distinct file content is searched once,
however many revisions hold it. Run it on the local ref that is pushed; the purge then proves the remote holds that same commit. Never run
it against a ref whose upstream still tracks un-purged history, which would false-alarm.

### responsibility:5 — GitHub-facing contracts

Owning the depended-on contracts GitHub holds the repository to: the files GitHub reads, pinned under
`contracts/catzc/<version>/Catzc.Tooling.Github/` at the path of the real file each one constrains under the module's target root, `.github`
([ADR-REPO-CONTRACT-LAYOUT](../../drs/repository/api-contracts.md#rule-adr-repo-contract-layout)), so `workflows/release-automation.yml`
pins `.github/workflows/release-automation.yml`
([ADR-REPO-CONTRACT-BINDINGINTERFACE](../../drs/repository/api-contracts.md#rule-adr-repo-contract-bindinginterface)). Each asset pins only
what GitHub reads, never an internal value
([ADR-REPO-CONTRACT-CONTRACTASSET](../../drs/repository/api-contracts.md#rule-adr-repo-contract-contractasset)): a workflow's `on` and each
job's `runs-on` and `steps` under `.github/workflows/`, and the presence of `.github/README.md`, the page GitHub renders first. The contract
mechanism in `Catzc.Base.Contracts` generates one test per asset, so a change GitHub would reject fails CI here first. A platform change is
a new draft in `contracts/catzc/0.0.0/`, never an old shape kept beside the new one
([ADR-REPO-CONTRACT-KEPTWHILEPINNED](../../drs/repository/api-contracts.md#rule-adr-repo-contract-keptwhilepinned)).

## What the module does

The module faces GitHub in both of GitHub's roles. As a platform, GitHub reads the repository's workflow files and its landing page; the
contracts pin what it reads, so the rest of each file stays free to change. As a remote, GitHub stores the history; the four erasure
responsibilities act on it.

The four erasure responsibilities form a single pipeline with the verification primitive threaded through both ends of it. A rewrite
produces a token-free local history; the preflight guards the irreversible move; the purge makes that history the remote's only history and
destroys the old objects with the repository that held them; and verification scans the local ref, then proves from the server's own refs
that the remote holds exactly that commit, so no step is trusted without proof of what the server stored. The rewrite offers two routes
because completeness and convenience trade off: rebuilding from a clean tree leaves nothing to scrub and no residual objects but discards
the original commit shape, while an in-place filter-repo scrub preserves it at the cost of unreachable leftovers and a blind spot on file
paths.

Safe-by-default is the through-line across the mutating surfaces. Every destructive entry point runs a dry run and returns a plan unless
explicitly armed with a confirmation value matching its target, and the remote purge keeps the local clone and the verified backup bundle
intact throughout, so any failure after deletion is recoverable from the exact commands it prints. The module holds no state and no config
of its own beyond its contract assets: it is a thin, ordered set of operations over `git`, `gh`, and git-filter-repo, each invoked through
[Catzc.Base.Execution](catzc-base-execution.md), returning structured results rather than writing to the console.
