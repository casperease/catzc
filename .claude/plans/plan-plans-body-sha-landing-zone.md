# Plan: body-sha policy, tracked plans, and an import landing zone

Three connected changes, in this order. Phase 0 changes how every later edit behaves, so it goes first.

- **Body hash only where it earns its place.** Every generated, git-tracked file carries an autogenerated head with a `body_sha`. Other
  files may carry one but never need to, and the tooling never nags about it.
- **Plans that stay true.** Live plans are tracked in `.claude/plans/`, kept short and current by rules and a cleaner. A plan that is done
  is deleted, always, because planning agents can die at any moment and the plan on disk is the state they leave behind.
- **`.unordered/` is the import landing zone.** An outside repository is imported with its history to a unique, simple landing address
  there, then sorted into modules in order. What is left in `.unordered/` is, by definition, the unordered part of this repository.

## Phase 0: the body-sha policy

1. **Generated and git-tracked: required, autogenerated, no exceptions.** The writer composes the head through the one head function, and the
   head holds `body_sha`, the hash of everything below it. This reaches the 264 diagram text files and the 2 compiled files, which have
   no head now, and puts a `body_sha` in the 12 that have one and the comment pages.
2. **Everything else: never required, never imprinted, removed.** About 650 authored pages carry one now (1,726 minus the comment pages,
   to be verified). One change removes them through `Format-FileMeta`. A body hash on an authored page is only annoying (decided), so the
   tool neither keeps one current nor demands one.
3. **A hand-added one is no finding (decided).** An author may keep a `body_sha` in a page; the tool leaves it alone and reports nothing,
   present or absent. It is the author's, and the tool does not maintain it.
4. **Where it lands.** `file-meta.yml` (`body-sha` selects the generated class, not all Markdown), `generated-head.yml` and
   `Format-GeneratedFileHead`, `Test-GeneratedFiles` (drift compares head and hash), `Get-BodyShaFileMetaFact`, FILEMETA#3 and #7, their
   tests, and the glossary if a term moves.

## Phase 1: the `.unordered` landing zone

**Terms, each defined by one ADR rule that bolds it (ADR-REPO-VOCAB#1).** An **import** brings an outside repository into this one with
its full history. A **landing address** is the folder `.unordered/<name>` an import lands at: a short kebab name, unique among the
addresses. **Sorting** moves a file from a landing address to its module or track with `git mv`, so history follows. The **unordered**
part of the repository is whatever is still under `.unordered/`. These replace the current wording of ADR-DSGN-TRACK#17 ("fragments frozen
when committed, such as finished plans"), the `unordered` entries in `track-types.md`, `tracks.md` and the glossary, and the `note` file kind.

**Tool, small on purpose.** `Import-RepositoryWithHistory -Source <path or url> [-Name <landing name>] [-DryRun]`: resolves the landing
name, fails if the address exists, checks the source is a clean git repository, and imports it under `.unordered/<name>` with every source
commit kept. It touches nothing outside `.unordered/<name>`. It runs only when you ask, since it changes git history. Tests use two
temporary repositories and prove the log is preserved and a taken name is refused. A how-to explains sorting. There is no getter that
reports the size or state of `.unordered/`.

**The landing name (recommended).** `-Name` is optional. The default is the source's folder or repository name in kebab case, one resolution
order with the explicit name winning ([ADR-AUTO-DEFAULT#6](../docs/adr/automation/sensible-defaults.md#rule-adr-auto-default6)). A name that
is not a short kebab word, or that is already an address, fails fast; the tool never adds a suffix to make it unique, so an address always
means what its name says.

**How the history is moved is left open.** `git subtree add` and a `git filter-repo` rewrite under the landing path both keep every source
commit; they differ in whether the source's own paths are rewritten. This is not researched further here. It is an open question below,
and the tool's contract (landing address in, commits kept, nothing outside it touched) does not depend on the answer.

**Bindings.** The ~27 references to `.unordered` are audited one by one: a measure or a track getter goes; a scan exclusion stays only where
a tool walks the disk and not the git index (ADR-AUTO-TRACKED). The `unordered` track class stays, because imported content is tracked.

## Phase 2: tracked plans and the cleaner

**Rules (for `ADR-REPO-PLANS`):** one topic per file, `.claude/plans/plan-<topic>.md`; a head with `status` (`active` or `blocked`),
`targets` and `refs`; no inline links in the text, every link target gathered into `refs`; at most 150 lines (a setting); open steps are
checkboxes that name the check proving them; present tense; every `targets` path exists; `reviewed:` stamped by the cleaner.
**A plan with no open step is deleted, always** (decided). Git keeps it.

**Cleaner.** A `plan-cleaner` sub-agent (registered with its rule, ADR-REPO-AGENTS) and a `Test-Plans` gate. Per plan it reads the plan,
skims its targets, gives a verdict with evidence (done, stale, blocked, live), and then acts: **done is deleted**, stale is shortened or
deleted, live has its links gathered and its text shortened, and `reviewed:` is stamped. It runs no git command; you commit.

**Promotion.** `Publish-Plan -Path out/plan-x.md` checks a draft against the rules and writes it to `.claude/plans/`; `Get-PlanCandidate`
lists drafts in `out/` by age. Regular basis: a manual command plus a `/plans` skill, with a schedule later.
The 20 plans in `.unordered/` are finished by the old rule, so triage deletes most of them first; survivors are moved and cleaned, one at a
time. `.claude/CLAUDE.md` changes from "plans go in `out/`" to "draft in `out/`, promote with `Publish-Plan`; delete a plan when done".
