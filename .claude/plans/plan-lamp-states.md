# Lamp language: one total union over the filters, any engine; the editor's lamps the first

The lamps are one renderer of a small, engine-neutral **lamp language**: a few rules over filters, a lit set and per-file facts, small
enough to implement in any engine or language. DDR-FILTER states the rules and a shared vector file pins them, so every engine is checked
against the same cases. The first engine is the JavaScript of `catzc-track-lamps`, feeding the language from what VS Code already knows.

## Why its value is high

The lamps are the user's daily view of the repository, and the same question ("what is in my view, and how is each part doing") is asked by
a pwsh query, a pipeline log or another editor. One language with shared vectors answers it the same everywhere (PDR-ONELIVE), and each
engine only adapts its own sources; the editor reproduces nothing VS Code already holds.

## The language

Inputs:

- **filters**: each a name and its sets `{ include, exclude }` (from `filters.yml` through `Get-RepositoryFilter`); `claims(f)` is the
  filters whose sets match file `f`.
- **lit**: the lamps the user has on.
- **facts** per file: `change(f)` one of `none`, `staged`, `unstaged`; `fault(f)` one of `none`, `failed`.

Rules:

1. **Total union.** `f` is shown while `claims(f) ∩ lit` is not empty. Every lamp takes part the same way, the languages lamp included; no
   lamp hides over another.
2. **Coverage.** `claims(f)` is never empty; a file no filter claims is shown and counted as unaccounted.
3. **Condition.** A lamp's condition is the highest fact over the files it claims, by one precedence: `failed` > `unstaged` > `staged` >
   `committed` (`committed` when no claimed file has a fact). It is independent of `lit`.
4. **Icon.** The icon is `table[lit or unlit][condition]`, nothing else.

## Decided (2026-10-24)

- The switch keeps today's feel: one click puts a lamp on or off, and a lamp's on/off never changes any lamp's condition.
- The languages lamp is a filter like the others: its sets are `**/*.<extension>` of the languages typed in its field, so the field names
  the languages to **show**, and, lit with the others out, it is a language view.
- Colours: committed green (`#3fb950` lit, `#1f6f3a` unlit ring), staged dark brown (`#7a4a1e`), unstaged yellowish (`#e0b83a`), failed red
  (`#f85149`, its unlit badge blinking). The icons exist as `<lamp>-<on|off>[-<staged|unstaged|failed>].svg`.
- The Explorer's git decoration colours follow the lamps (staged dark brown, unstaged yellowish), one mapping in the repository.
- The VS Code engine reads the facts from the sources of the Explorer's own colours; an extension cannot read another's decorations, so it
  reads what they are drawn from, never pwsh or a spawned git, its one watcher the test-result markers':
  - `change` from the built-in git extension's API (`vscode.git`, `getAPI(1)`): `staged` for `state.indexChanges`, `unstaged` for
    `workingTreeChanges`, `untrackedChanges` and `mergeChanges` (unstaged winning when a file is in both), recomputed on the repository's
    `state.onDidChange`.
  - `fault` from the diagnostics (`vscode.languages.getDiagnostics`, `onDidChangeDiagnostics`): `failed` while the file carries an Error
    diagnostic, so a fix lapses red by itself.
- The JavaScript is split in two: a pure core `evaluate(filters, lit, facts)` returning the shown set, each lamp's condition and the
  unaccounted files, with no `vscode` import; and the adapter that turns VS Code's sources into facts and the core's answer into
  `files.exclude`, context keys and the counter.
- No domain SHA is computed in an engine of the language; the durable globset SHA stays the pipelines' (FDR-CD-GLOBS-DURABLESHAIDENTITY).
  - `fault` also from the test-result markers: `Invoke-TestFile` keeps `out/test-results/<repository path of the test file>.failed`, written
    when the file fails and deleted when it passes; VS Code exposes no test results to other extensions, so the marker is the indirect
    route. The adapter watches `out/test-results/**` and reads only existence and timestamps, never Pester output: a marker makes its test
    file `failed` while it is newer than the test file and every file of the test's module, so an edit after the run lapses red to the
    change's brown. Any later producer (`Test-Automation`, a gate, a CI download) writes the same markers and the extension is unchanged.
- The markers are a long-lived area of their own in `output-formats.yml` (ADR-REPO-OUTDIR-EVERYFILEHASFORMAT), never the stamped run folders
  `Clear-Output` clears; `out/test-results` stays out of `files.watcherExclude`, while `files.exclude` hiding `out` leaves the watcher
  working.
- The manifest's state commands and icons expand from `filters.yml` × the states in the folder generator; a new filter stays one config
  line.
