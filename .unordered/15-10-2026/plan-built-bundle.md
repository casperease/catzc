# Final plan: the built bundle and its consumer overlay

One plan for all of it:

- **A. Deterministic partial bundles:** the same commit and selection give the same bytes on any OS.
- **B. The consumer overlay:** `.catzc/` in the consumer's `RepositoryRoot`, with its ruleset (draft ADR below).
- **C. "built" as the normative past tense:** for the built bundle and the built types assembly.
- **D. The bundle as an engine:** one command line, the same bytes, in every environment.

It sequences together with the drift plan (`out/plan-explanation-drift.md`). Its D-RUN row is settled here.

Governing domain rules: ADR-AUTO-BUNDLE, ADR-DSGN-RUNMODE, ADR-AUTO-DEFAULT#6, ADR-AUTO-ASSETDEP, ADR-PWSH-ONEFUNC, ADR-CONF loading,
ADR-AUTO-TEST, ADR-REPO-VOCAB, ADR-AUTO-PARITY, ADR-FLOW-CD#3, ADR-FLOW-CD-RUNNER, ADR-PRIN-ONELIVE, ADR-AUTO-FAILFAST.

## B. The consumer overlay: `.catzc/`

### B.1 Layout

```text
<RepositoryRoot>/                                    the consumer's own working root
  importer.ps1                                       written by Export-Catzc -Root; loads the bundle (+ overlay)
  .vendor/Catzc/<v>/                                 the built bundle — read-only engine code
  .catzc/                                            THE OVERLAY — optional, committed by the consumer
    catzc.yml                                        overlay settings (every key has a declared default)
    automation/                                      mirrors the bundle's code root, path for path
      Catzc.Azure.Cli/                               named for a BUNDLED module → changes that module
        Invoke-AzCli.ps1                             replaces public function Invoke-AzCli
        private/Get-AzCliPath.ps1                    replaces private function Get-AzCliPath
        configs/azure.yml                            fragment: only the keys that differ
        assets/templates/main.bicep                  replaces that bundled asset file
        tests/Invoke-AzCli.Tests.ps1                 local test of the effective (overridden) module
      Widget.Deploy/                                 any other name → a LOCAL module
        Deploy-Widget.ps1
        private/Get-WidgetPlan.ps1
        configs/widget.yml
        assets/…
        tests/Deploy-Widget.Tests.ps1
  out/                                               everything catzc derives (merged configs, local manifests, reports)
```

### B.2 Ruleset: draft `ADR-AUTO-OVERLAY` (`docs/adr/automation/consumer-overlay.md`)

**ADR-AUTO-OVERLAY:1. The overlay.**

- A consumer's **overlay** is the `.catzc/` folder at its `RepositoryRoot`. It is the only place a consumer changes what a built bundle
  does. The bundle under `.vendor/Catzc/<v>/` is read-only and never edited.
- The overlay is optional, and so is every file in it. With no overlay, the bundle runs exactly as built.
- The overlay is the consumer's source: committed, reviewed, and never written by catzc. Everything catzc derives from it goes under the
  working root's `out/`.

**ADR-AUTO-OVERLAY:2. The mirror rule: the location is the meaning.**

- A file under `.catzc/automation/` sits at the same relative path as the thing it changes under the bundle's code root.
- The path alone says what is overridden. No registry, list or manifest of overrides exists, so nothing can disagree with the files.

**ADR-AUTO-OVERLAY:3. A closed set of override points.**

Within `.catzc/automation/<Module>/`, where `<Module>` is a bundled module, the only valid entries are:

| Location                 | Overrides                                       | Rule |
| ------------------------ | ----------------------------------------------- | ---- |
| `<Function>.ps1`         | the public function `<Function>` of `<Module>`  | #5   |
| `private/<Function>.ps1` | the private function `<Function>` of `<Module>` | #5   |
| `configs/<config>.yml`   | the config `<config>` that `<Module>` owns      | #4   |
| `assets/<path>`          | the bundled asset file at `assets/<path>`       | #6   |
| `tests/**/*.Tests.ps1`   | nothing; local tests of the effective module    | #8   |

A folder that names no bundled module is a local module (#7). Anything else is rejected at load: `types/`, `.internal/`, `.vendor/`,
`.compiled/`, a `.psd1` or merged `.functions.ps1`, or an unknown subfolder or file kind. Adding an override point is an amendment to this
rule.

**ADR-AUTO-OVERLAY:4. Config fragments and one resolution order.**

- A config file in the overlay is a **fragment**: it states only the keys that differ.
- In built mode, a setting resolves in this fixed order, which extends ADR-AUTO-DEFAULT#6 by one step:
  1. the caller's explicit value;
  2. the overlay fragment;
  3. the bundled module config;
  4. the default declared once on the config type.
- A missing fragment, a missing key, or a fresh consumer root therefore all fall through to the bundle and then to the type's default.
  Nothing has to be copied in order to change one value.
- Merge semantics, by key path (the `Get-ConfigValue` addressing):
  - maps merge recursively;
  - scalars and lists **replace**, never append;
  - an explicit `null` **resets** the key to its declared default.
- The merged result is constructed and validated by the same C# config type, so an override can never produce a config the engine would
  reject.
- A key the type does not know is rejected, with the type's list of valid keys.

**ADR-AUTO-OVERLAY:5. Function overrides: one per named file.**

- `<Function>.ps1` (or `private/<Function>.ps1`) holds exactly one function named for the file, under the same preconditions as a bundle
  merge (`Get-MergePreconditionViolation`).
- It **replaces** that function inside the bundled module's own scope. Catzc's callers, the module's `$script:` state, `Get-Command`,
  `Mock -ModuleName`, and calls from other modules all reach the override.
- The function must already exist in that module, with the same visibility (public stays public, private stays private). An override of a
  missing function is a typo and throws.
- **New** functions do not go into a bundled module; they go in a local module (#7).
- The **contract** is kept, so catzc's own callers still work:
  - the parameter set is a superset of the original's;
  - no new mandatory parameter;
  - the same parameter types;
  - the same `[OutputType]`.

**ADR-AUTO-OVERLAY:6. Asset overrides.**

- `assets/<path>` replaces the bundled file at that path.
- `Get-CatzcModuleRoot` resolves an asset in the overlay first, then in the bundle. It is the only asset lookup there is
  (ADR-AUTO-ASSETDEP#1), so every inventoried asset read sees the override.
- An override must replace an existing bundled asset. New assets belong to a local module.

**ADR-AUTO-OVERLAY:7. Local modules.**

- A folder under `.catzc/automation/` that names no bundled module is a **local module**. It follows the same conventions as catzc's own
  modules:
  - folder = module;
  - one function per file;
  - public by location at the root, private under `private/`;
  - `configs/` registered as usual;
  - `assets/`;
  - `tests/`.
- Its manifest is generated under `out/`, never in `.catzc/`.
- It never takes the reserved `Catzc.` prefix: a `Catzc.*` folder that is not bundled is a missing module or a typo, and it throws.
- It carries no `types/`: a bundle has no Roslyn at load, so C# types come only from the built types assembly.
- It may call any bundled public function. It loads after the bundled modules and their overrides.

**ADR-AUTO-OVERLAY:8. Local tests.**

- `tests/` under any overlay module folder holds the consumer's tests.
- They run in built mode against the **effective** session (bundle + overrides + local modules), through the one test harness
  (`Invoke-TestFile`, the levels, the report).
- A test run needs a test-capable bundle (`vendor_policy: full`: Pester and the TestKit). Without one, the run fails with one assert naming
  the fix.

**ADR-AUTO-OVERLAY:9. Sealed surface.**

- The bundle declares what no overlay may change, in one config, `overlay.yml`, owned by the overlay module. Its default seals:
  - the engine-intrinsic configs: `configs`, `dependencies`, `profiles`, `exporter`, `overlay`, and the glossary sources;
  - the guard functions a module lists there (for example the auth rungs).
- Touching a sealed item throws.
- Sealing is configuration, so making something overridable is a reviewed config edit, never code.

**ADR-AUTO-OVERLAY:10. Applied in one order, verified as a whole.**

- In built mode the importer applies the overlay in one fixed sequence:
  1. bundled modules;
  2. function overrides;
  3. local modules;
  4. the overlay asserts;
  5. the load banner.
- Config fragments merge lazily on the first `Get-Config` read. The merge cache is keyed by the fragment's content hash.
- Every rule of this ADR is checked together, and all violations are thrown as one list.
- `Test-CatzcOverlay` runs the same checks without loading, for a consumer's CI.
- Provenance is always answerable:
  - the banner names the overlay and counts its overrides;
  - `Get-CatzcOverlay` lists every override (kind, module, target, file);
  - `Get-Config -Provenance` shows which layer each key came from.

**ADR-AUTO-OVERLAY:11. Overlay settings and pins.**

- `.catzc/catzc.yml` holds the overlay's own settings. Every key has a default declared on its config type, so the file is optional.
- It may pin the bundle it was written for, as assert-is guards: `bundle.name`, `bundle.version`, `bundle.content_hash`. A mismatch throws
  at load, before any override is applied.
- The default is no pin.

**ADR-AUTO-OVERLAY:12. Built mode only.**

- The overlay applies only in built mode.
- In source mode the catzc tree _is_ `automation/`, and changes are made there directly, so a `.catzc/` folder in a source root is reported
  and ignored.
- The mono repo's own built run (`Test-BuiltBundle`) has no `.catzc/`, so it tests the bundle as built.

## C. "built", the normative past tense

**Rule.** The act keeps **build** (`Build-Modules`, "to build", `Build-CombinedTypeAssembly`). The thing that exists afterwards is
**built**: the **built bundle**, the **built types assembly**, **built mode**, a **built root**, a **built run**. The CI build, ADO build
validation, the BVT, `Build-Bicep` and `dotnet build` keep their own words, and the glossary contrasts say why (ADR-REPO-VOCAB#4).

| Today                                        | Becomes                                     |
| -------------------------------------------- | ------------------------------------------- |
| build mode, `Get-CatzcRunMode` → `build`     | built mode, → `built`                       |
| build root, build kind, kinds of build root  | built root, built kind, kinds of built root |
| build run, `Test-CatzcBuild`                 | built run, `Test-BuiltBundle`               |
| a build / the build (the artifact)           | the built bundle / a bundle                 |
| `out/automation/build/`                      | `out/automation/built/<bundle>/`            |
| `build.json`                                 | `built.json`                                |
| `Resolve-CatzcBuildVersion`                  | `Resolve-BundleVersion`                     |
| combined types assembly / the types DLL      | the built types assembly                    |
| glossary forms "build facet", "build run(s)" | "built facet", "built run(s)"               |

- **Gate:** a glossary source `Catzc.Base.Exporter/configs/glossary.yml` defines the five "built" terms (each bolded by its ADR rule) and
  lists the avoided phrasings `build mode`, `build root`, `build run`, `build kind` and `build-mode`, each with its replacement.
- **Execution:**
  1. Rename functions, files, paths and the run-mode value first, together with every caller, in one change (no aliases, ADR-PRIN-ONELIVE).
  2. Then hand the prose to `catzc-worker` in scoped batches (code help, tests, ADRs, explanation, how-to, glossary). Edit one file at a
     time; no sed sweeps. Each batch reports every "build" hit it kept, with the reason.

## D. The bundle as an engine

| #   | Property                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | **One command line everywhere.**<br>• Every bundle ships `catzc.ps1`: `pwsh -NoProfile -File <bundle>/catzc.ps1 [-RepositoryRoot <dir>] -Command '<command>'`.<br>• It loads the bundle plus the overlay, runs the same command string a developer types after `. ./importer.ps1`, and maps the outcome to an exit code.<br>• A terminal, a pipeline step, a container `ENTRYPOINT` and a remote run-command all use this one line.<br>• `pipelines/Invoke-AdoScript.ps1` becomes a thin caller of it (ADR-FLOW-CD-RUNNER, one living runner).<br>• _Idea from eac_, weighed rather than copied: one launcher plus a reference container image (pwsh 7.4 + one built bundle). It stays a `.ps1` here (ADR-AUTO-GO). |
| D2  | **Build once, run the same bytes (ADR-FLOW-CD#3).** The CI stage builds each bundle once and publishes it as the artifact. Every later stage and target runs that artifact after `Assert-CatzcBundle`. The bundle that passed the BVT is, byte for byte, the engine that reaches prod. This is the automation unit's promoted artifact, so it ties into D-LAD in the drift plan.                                                                                                                                                                                                                                                                                                                                    |
| D3  | **Bare-host load.** Only pwsh 7.4 is needed: no git, no Roslyn, no fetch. Tools (`az`, `bicep`, …) are asserted per command (`Assert-Tool`), never at load, so only the command that lacks its tool fails.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| D4  | **Footprint as a budget.** `max_files` and `max_bytes` per bundle (A4), checked by `Assert-CatzcBundle`. A cold-load budget per bundle in `timeouts.yml`, checked by the L1 load test.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| D5  | **Read-only code, writable root.** The bundle may sit on a read-only layer. Every write goes under `<RepositoryRoot>/out/`. Extend the walking-skeleton test to a read-only bundle folder with an overlay.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| D6  | **Self-identifying session.** Build `Write-CatzcLoadBanner`: mode, bundle, version, `contentHash`, commit, dirty, overlay root, override counts and local modules. A remote log must say what ran.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

**Settles drift D-RUN:** the banner is built (D6); `build-catzc.ps1` and the "cached" built kind are **cut** from ADR-DSGN-RUNMODE. A cache,
if one is ever needed, is plain caching keyed by `contentHash`, not a run-mode kind.

| #   | Decision                       | Applied default                                                                                                               |

| G1  | Overlay root                   | `.catzc/` at the `RepositoryRoot`, mirroring the code root under `.catzc/automation/`. Fixed by convention, not configurable. |

- **B1 (function override) is the one unknown**, which is why phase 3 is the spike. A fallback to whole-module replacement would change rule
  #5, and the plan says so up front.
- **Git-blob builds need git at build time.** Building is already a source-tree act (`Assert-SourceTree`), so this adds no new requirement.
- **The vocabulary pass touches about 440 files** that other sessions also edit. Coordinate each batch.
